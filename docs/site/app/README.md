# Platform Explorer: how it works and how to add screens

`docs/site/app.html` is a static, no-build mock of the whole Rootline platform. It opens from `file://`, has no server and no framework. Every screen is gated by **role**, **package** (plan), **market** (sample tenant) and **scope lens** using the same data a real build would use.

## Files and load order

| File | What it holds |
|---|---|
| `assets/platform-data.js` | `window.ROOTLINE_PLATFORM`, generated by `python3 docs/platform/build.py` from `docs/platform/*.json`. Never edit by hand. |
| `app/core.js` | Indexes (`RL.idx`), state and hash routing (`RL.S`, `RL.set`, `RL.go`), the gating engine (`RL.access`), the context object (`RL.ctx`), the screen registry (`RL.screen`), the render loop and event delegation. |
| `app/ui.js` | `RL.h`: the HTML helper library. Every helper returns a string. |
| `app/icons.js` | The SVG icon sprite. `RL.h.icon('name')`. |
| `app/data.js` | `RL.data(tenant)`: deterministic sample data per tenant (clients, jobs, visits, invoices, designs, ledger and more). |
| `app/frames.js` | Explorer bar, one frame per surface (web app, console, crew phone, sub lite, portal, partner hub, marketing site, Rootline Home), permission states and the "Why you see this" lens. |
| `app/atlas.js` | Atlas pages: overview, personas, roles and access, packages, markets, who sees what, every screen. |
| `app/screens-*.js` | Screens, one file per area. |
| `app/tools/check.js` | Playwright checker (see Testing). |

## The state and the URL

The hash holds the whole view: `#r=web.today&as=owner&t=greenleaf&plan=pro&scope=mvp&season=winter&lang=es&x=J-1042`.

| Key | Meaning |
|---|---|
| `r` | Route id from `docs/platform/surfaces.json`, or an atlas page (`atlas.home`, `atlas.personas`, ...). |
| `as` | View-as key: a role (`owner`), or a client role plus contact scope (`client_commercial.approver`). The list is `RL.AS`. |
| `t` | Sample tenant id from `tenants.json` (each is one target market). |
| `plan` | Plan override. Empty means the tenant's own plan. |
| `scope` | Scope lens: `mvp`, `v1`, `v2` or `all`. |
| `season` | `peak` (Tue May 11, 2027) or `winter` (Tue Jan 12, 2027). |
| `lang` | `en` or `es`. Choosing a crew role switches to `es`. |
| `x` | Record id for detail routes (`/jobs/:id` and so on). |

## Gating (what decides whether a screen shows)

`RL.access(route, state)` applies, in order: the role must use the route's surface (`RL.SURF`); `route.roles` if present; navigation visibility from `roles.json` (21 §5.4, §5.5, §5.9); the permission named in `route.perm` (02 §10.1); the module in `route.module` (hidden, not greyed out); the plan feature in `route.feature` (22 §4.2.1). Results: `ok`, `limit` (included with a limit), `locked` (owner sees an upgrade prompt), `hidden`, `denied`, `off`, `surface`. Denied states render the permission state from 21 §5.8. You never need to re-check route-level gating inside a screen.

Inside a screen, gate **parts** of the page:

```js
c.has('design_3d')            // plan includes it (Y or L, or bought as an add-on)
c.feat('automations')         // { s: 'Y'|'L'|'A'|'-', note, addon, unlock: [...] }
h.lock(c, 'design_3d')        // inline upsell card (only meaningful for the owner)
c.allowed('invoice.void')     // role holds any grant other than '-' for the capability
c.can('estimate')             // raw grant string, e.g. 'RWD/o + R/b'
c.sees('margin')              // field class visible to this role (02 §10.2)
h.mask(c, 'cost', h.money(n)) // value, or ••• with a tooltip naming the rule
c.mod('lawn_programs')        // tenant has the module enabled
c.inLens('V1')                // the scope lens includes V1; tag later features with h.tag('V1')
```

## Writing a screen

Wrap each file in an IIFE and register screens by route id:

```js
(() => {
'use strict';
const RL = window.RL, h = RL.h, { esc, icon, money } = h;
RL.screen('web.jobs', (c, a) => {
  const rows = c.D.jobs;
  return h.page({ title: 'Jobs', sub: `${rows.length} open`, actions: c.allowed('job') ? h.btn('New job', { kind: 'primary', icon: 'plus', act: 'new-job' }) : '' })
    + h.table([
        { k: 'id', label: 'Job', m: true },
        { k: 'client', label: 'Client' },
        { k: 'value', label: 'Price', n: true, fmt: v => h.mask(c, 'price', money(v)) },
      ], rows, { go: 'web.job' });
});
RL.act('new-job', (el, ev, c) => { RL.toast('Job created (mock)'); return false; });
})();
```

`c` (the context) has: `t` (tenant), `seg` (segment), `plan`, `planCode`, `role`, `roleObj`, `as` (view-as option), `scope` (client contact scope), `who` (person's display name), `owner` (owner's name), `route`, `surface`, `x` (record id), `D` (sample data), `season`/`winter`, `lang`/`es`, `tr(en, es)` (translate), `today` (`{ label, short, month, dow }`), plus the gating helpers above. The second argument `a` is the access result; `a.state === 'limit'` carries `a.limit`.

`c.D` (from `RL.data`) has: `crews`, `people`, `clients`, `properties`, `leads`, `opps`, `estimates`, `proposals`, `jobs`, `visits` (today's stops, with x/y for maps), `agreements`, `invoices`, `payments`, `aging`, `designs`, `plants`, `kpi`, `accounts`, `journal`, `bank`, `timesheets`, `equipment`, `inventory`, `vendors`, `campaigns`, `reviews`, `agents`, `res` (the residential client cast) and `com` (the commercial client cast). Read `app/data.js` for field names.

## Interactions (no framework, all delegated)

| Attribute | Effect |
|---|---|
| `data-go="route" data-x="id"` | Navigate (keeps role, tenant and plan). |
| `data-ui="key" data-val="v"` | Set `RL.ui[key] = v` and re-render. Use for tabs, toggles, selections and step-by-step flows. `h.tabs`, `h.toggle` use it. |
| `data-ui-input="key"` | On inputs and selects: store the value in `RL.ui[key]` on change. |
| `data-act="name"` | Call `RL.act(name, (el, ev, c) => ...)`. Return `false` to skip the re-render. |
| `data-modal="name"` | Open `RL.modal(name, c => ({ title, body, foot }))`. |
| `data-set="as=owner&r=web.today"` | Change explorer state (used by the atlas). |

Phone surfaces (crew, manager mode, sub lite, portal in phone mode, Rootline Home) put everything before `<!--side-->` inside the phone; anything after it renders in a side panel next to the phone (use it for "what the office sees" notes).

## Rules every screen follows

- Data and copy are illustrative. Use the tenant's cast and `c.D`; never present a real company as a customer, partner or endorser. Competitor names appear only on factual compare and switch pages, with a "verify" note.
- Iris (`ai` tone, `h.aiCard`, `.btn.ai`) is reserved for AI output. Every AI action shows its credit cost (22 §4.4.1) and autonomy level (L0-L4) before it runs. Tier T4 actions (charging a card, signing) are never done by AI.
- Respect field classes: crews never see prices, costs or margins; subcontractors never see the Company's sell price; bookkeepers see billing fields, not gate codes.
- Never block a Company from getting paid: invoicing, portal payments and the ledger stay available in every plan and dunning state.
- Plain language, sentence case, no em dashes. No delivery dates or effort estimates; scope uses MVP, V1, V2, V3 tags.

## Testing

```bash
python3 docs/platform/build.py                 # after editing docs/platform/*.json
node docs/site/app/tools/check.js web.         # one area; or no prefix for everything
node docs/site/app/tools/check.js crew. --shots=/tmp/shots
```

The checker opens every matching route as every view-as option on that surface, on four tenants and two plans, clicks each interactive control once, and exits non-zero on page errors, console errors, empty screens or routes with no registered screen.
